# AI 辅助项目开发 Harness —— 流程与注意事项

> **用途**：本文档是"AI 辅助开发"的通用流程框架（harness）与经验库（skill），由**资政大模型**项目（大一年度项目，RAG/智能体方向）实战复盘提炼，可直接复制到其他项目使用。
> **适用范围**：AI 智能体（Agent）主导或辅助的软件工程项目：RAG、NLP、数据工程、Web 应用等。
> **来源项目**：资政大模型——基于垂直领域大模型的政府智库报告生成智能体（160 篇政务语料 / DC-RAG / 自研智能体应用）。

---

## 一、总体工作流（7 阶段）

```
阶段 0  规划立项    解读需求/立项文档 → 生成任务清单 → 生成项目要求（盘点/验收）
阶段 1  资产保全    版本管理 + 远程备份 + 目录规范（最高优先级，先做！）
阶段 2  数据层      盘点 → 元数据 → 清洗流水线 → 爬虫/增量 → 清洗入库
阶段 3  知识库      嵌入选型 → 切分 → 摘要 → 聚类 → 树形索引 → 导出备份
阶段 4  检索与生成  输入增强 → 检索 → 质量评估 → 生成 → 对比记录成文档
阶段 5  应用与合规  Web 应用 → 安全合规（过滤/审计）→ 部署文档
阶段 6  集成与验收  端到端联调脚本 → 结题/交付材料
```

**核心原则**：
1. **文档先行**：动手写代码前，先产出任务清单（以结题/交付目标为导向）与需求文档（含现状盘点、验收标准）。
2. **随做随提交**：每个模块完成即 `git commit` + `git push`，杜绝"开发完再统一提交"。
3. **可复现优先**：所有数据处理流程脚本化（清洗、向量化、聚类一键可跑），避免"数据好了但脚本丢了"。
4. **对比出结论**：涉及方法选型（如 DC-RAG vs 扁平检索），用评测集量化对比并记录成文档，用数据说话。

## 二、各阶段详细流程

### 阶段 0：规划立项

| 项 | 内容 |
| --- | --- |
| 输入 | 立项报告 / 需求文档 / 口头目标 |
| 产出 | ① 结题任务清单（目标导向，含模块划分、交付物、完成标准）② 项目要求文档（现状盘点：已有/缺失资产；功能与非功能需求 FR/NFR；验收标准） |
| 注意事项 | 任务清单以**交付目标**而非过程为导向；明确"验收要点"列表；对已有资产做差距分析 |

### 阶段 1：资产保全（最高优先级）

| 项 | 内容 |
| --- | --- |
| 步骤 | `git init` → `.gitignore` → 首次提交 → 建远程仓库并 push → 目录规范 + README |
| 交付物 | git 仓库、远程备份、README（目录结构/文档索引/进度） |
| 完成标准 | 现有资产全部纳入版本管理 |
| 注意事项 | **本项目曾因无版本管理丢失全部代码**。任何已有资产（数据、配置、文档）先入库再开发 |

### 阶段 2：数据层

| 步骤 | 交付物 | 注意事项 |
| --- | --- | --- |
| 数据盘点 | 清单 CSV（文件名/大小/编码/预览） | 校验编码（UTF-8）、空文件、残缺 |
| 元数据标注 | 元数据 CSV（级别/区域/年份） | 历史行政区名归一化；用脚本生成而非手工 |
| 清洗流水线 | 可复现清洗脚本 + 清洗报告 | 去 BOM/TAB/全角空格、压缩空行、正文起点识别、残缺检测 |
| 爬虫/增量 | 爬虫 + 配置 + 抓取样例 | 增量去重；多轮重试；失败回退协议 |

### 阶段 3：知识库

| 步骤 | 关键点 | 坑点提醒 |
| --- | --- | --- |
| 嵌入选型 | 中文选 BGE 系；本地 CPU 用小模型（bge-small，512 维） | 查询侧需加检索指令前缀；大模型权重不入库（.gitignore） |
| 文档切分 | 标题独立成块、超长按句切分、短段并入 | 块长设上限（≤512），携带元数据 |
| 摘要生成 | LLM 生成式 + 提取式双模式 | **推理模型 max_tokens 要 ≥1500**，否则 content 为空 |
| 聚类 | PCA 降维 + BIC 选类 + GMM 软聚类 | 自动选 k 可能过粗，可人工细化 k 提升区分度 |
| 树形索引 | 类别→文档→文本块三级 | JSON key 注意 int/str 类型 |
| 导出备份 | 文档级 + 文本块级标准 JSONL | 使用通用格式，避免绑定平台专属标识符 |

### 阶段 4：检索与生成

| 步骤 | 关键点 |
| --- | --- |
| 输入增强（C1） | LLM 改写查询（补全上下文/提取主题地域时间），失败回退原文，temperature 宜低（0.2） |
| 检索（C2） | 三级顺序检索；同时实现扁平基线供对比 |
| 评估（C3） | 建立评测集（覆盖各层级/主题，标注 gold 文档），文档级 + 块级双指标 |
| 生成（C4） | 提示词要求引用来源、结构化输出、资料不足给建议；**双路检索融合**缓解年份偏移 |

### 阶段 5：应用与合规

| 步骤 | 关键点 |
| --- | --- |
| Web 应用 | Flask + 聊天界面；接口返回答案 + 来源 + 增强查询 |
| 安全合规 | 输入/输出双侧敏感词过滤；审计日志（ask/blocked/error）；密钥 .env 不入库 |
| 部署文档 | 本地部署步骤 + 政务云/内网方案 + 验收对照表 |

### 阶段 6：集成与验收

| 步骤 | 关键点 |
| --- | --- |
| 端到端联调脚本 | 数据层→知识库→检索→生成→应用逐层检查，快速模式（无 LLM）+ 完整模式（含 LLM），输出 JSON 报告 |
| 结题材料 | 结题报告（概述/架构/实施/成果/评估/对照）、演示材料、成果物清单 |

## 三、工具与环境规范

### 3.1 Git 提交规范

- 提交信息：`type: 简述`（`feat:`/`fix:`/`docs:`/`refactor:`），一行标题 + 可选多行正文。
- **逐个 add 指定文件**，避免 `git add -A` 误入敏感文件（.env、凭据）。
- 敏感文件用 `.gitignore` 前置拦截，若误提交用 `git rm --cached` 清理。
- PowerShell 下提交多行信息用多个 `-m` 参数（`git commit -m "标题" -m "正文"`）。

### 3.2 环境与依赖（Windows / PowerShell）

- 依赖安装慢时用国内镜像：`pip install -i https://pypi.tuna.tsinghua.edu.cn/simple ...`。
- 模型/大数据产物（models/、data/vectors/、*.npy）一律 `.gitignore`。
- 密钥统一走 `.env` + `.env.example` 模板，代码内不硬编码。

### 3.3 文档规范

- 每个模块交付物留痕：任务清单打勾 + 交付物路径 + 完成标准实测结果（写"实测：xxx 命中/通过"而非"测试通过"）。
- 评估、对比结论必须记录成独立文档（如检索评估报告），附复现命令。

## 四、踩坑记录与规避方法（实战教训）

> 以下为本次项目真实遇到的问题与解决方案，按可迁移性排序。

### 4.1 环境与工具类

| # | 坑 | 现象 | 解决/规避 |
| --- | --- | --- | --- |
| 1 | PowerShell 不支持 heredoc | `<<'EOF'` 报错 | 用 `git commit -m "a" -m "b"` 多参数 |
| 2 | 内联 python 与管道符冲突 | `python -c "... | ..."` 被 shell 解析 | 复杂逻辑写脚本文件而非 `-c` 内联 |
| 3 | torch 官方源极慢/卡死 | pip 安装长时间无进展 | 改用清华镜像 `-i https://pypi.tuna.tsinghua.edu.cn/simple` |
| 4 | HTTPS TLS 握手失败 | 政务站点报 `BAD_ECPOINT` | 回退 http 协议访问 |

### 4.2 数据处理类

| # | 坑 | 现象 | 解决/规避 |
| --- | --- | --- | --- |
| 5 | 页眉误判 | "各位代表！"被当作页眉删除 | 维护 `IGNORED_HEADERS` 白名单，结合上下文判断 |
| 6 | 残缺文件 | 仅网页导航无正文 | 用正文起点特征词检测并标记 `suspicious_empty_body`，不入知识库 |
| 7 | 正文起点误判 | 光明/龙华法治报告被截断 | 正文起点特征词补充"报告如下"等 |
| 8 | CSV 合并类型错误 | int vs str 冲突 | 读取历史数据时显式类型转换 |

### 4.3 模型与算法类

| # | 坑 | 现象 | 解决/规避 |
| --- | --- | --- | --- |
| 9 | LLM 返回空内容 | 推理模型 max_tokens=300 不够，content 为空 | max_tokens ≥1500（推理 token 单独消耗）；空内容显式报错 |
| 10 | 检索命中率低（17%） | 文档级 Recall@3 仅 2/12 | ①文档向量改用 LLM 摘要向量（17%→58%）②查询加 BGE 前缀 ③聚类细化 k=3→8 |
| 11 | 年份偏移 | 增强查询把 2023 问成 2024 | 双路检索融合：增强查询 + 原查询分别检索，合并去重后取 top-k |
| 12 | JSON 键类型 | 聚类概率按 `str(cid)` 索引 | 注意 JSON key 全为字符串，取值时转 int |
| 13 | 平台绑定 ID | 专属配置和数据标识符无法跨环境迁移 | 核心链路自研，数据使用通用格式导出备份 |

### 4.4 工程管理类

| # | 坑 | 现象 | 解决/规避 |
| --- | --- | --- | --- |
| 14 | 代码全部丢失 | 管理不善，仅剩数据与 yml | 阶段 0 资产保全最先做；随做随提交 |
| 15 | 误提交环境文件 | `.env copy.example` 被 commit | `.gitignore` 前置拦截 + `git rm --cached` 清理 |
| 16 | 模型/向量入库 | 仓库体积爆炸 | `.gitignore` 忽略 models/、data/vectors/、data/knowledge_base/、*.npy |

## 五、质量保障 Checklist（每阶段自检）

```
□ 交付物是否按任务清单逐一落地，路径可点击
□ 完成标准是否有"实测数据"（命中数、通过数、耗时）
□ 是否已 git commit + git push（远程确认）
□ 数据/模型产物是否未入库（.gitignore 生效）
□ 是否产出对应文档（任务清单勾选 / 评估报告 / 部署文档）
□ 是否可复现（脚本一键重跑，不依赖"一次性人工操作"）
□ 密钥是否只存在于 .env（不入库、不入代码）
```


### 6.2 端到端联调脚本骨架

```python
# 逐层检查：数据层(盘点/元数据/块/摘要) → 知识库(向量/索引) → 检索(方法A+基线)

# 汇总写入 report.json，全部 PASS 返回 0；提供 --with-llm 区分快速/完整模式。
```

```python
# 输入/输出双侧 check_content()（内置红线词表 + 自定义词表文件，可扩展）
# audit_log() 追加 data/logs/audit.jsonl（event: ask/blocked/error + 来源 + 耗时）
# 密钥 .env 不入库；模型权重/向量 .gitignore
```

## 七、总结

AI 辅助项目开发的关键不在于"写得多快"，而在于**流程闭环**：规划先行 → 资产保全 → 分层实施（每层可验证）→ 对比出结论 → 安全合规 → 联调验收，全程文档留痕、随做随提交。本文档的踩坑清单（尤其是检索质量优化与平台依赖规避）可直接迁移到其他 RAG / 智能体项目。
